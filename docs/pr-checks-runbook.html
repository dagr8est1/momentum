How PR checks run on this repo

Every pull request opened against main or master triggers one workflow, named PR checks, with two independent jobs: a pytest run gated to feature branches, and a request for GitHub Copilot to review the diff. Both were built and iterated on directly against feature/ci-pr-tests (PR #2). This page is a working reference for how each piece fires, what it does, and how to switch it on or off.

01 What triggers the workflow

GitHub fires a pull_request event on four actions — opened, synchronize (a new push), reopened, and ready_for_review. Both jobs listen to all four, but each has its own gate that decides whether it actually runs.

02 Job: pytest Actions

Only runs when github.head_ref starts with feature/ or feature- — PRs from other branch names skip this job entirely rather than failing it. When it runs: checks out the repo, sets up Python 3.12 and uv, installs the dev dependency group, then runs the full suite.

full-tests.yml — pytest jobruns-on: ubuntu-latest
jobs:
  pytest:
    if: startsWith(github.head_ref, 'feature/') || startsWith(github.head_ref, 'feature-')
    steps:
      # checkout, setup-python 3.12, setup-uv (cached)
      - run: uv sync --group dev
      - run: uv run pytest

03 Job: request-copilot-review Copilot

Runs whenever the PR isn't a draft. It doesn't run any review itself — it just asks GitHub to add @copilot as a reviewer, using the GitHub CLI with the workflow's own token. Copilot then reviews asynchronously, the same way it would if a human had requested it from the PR sidebar.

full-tests.yml — request-copilot-review jobpermissions: pull-requests: write
request-copilot-review:
    if: github.event.pull_request.draft == false
    permissions:
      pull-requests: write
    steps:
      - env: GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh pr edit "$PR_NUMBER" --repo "$REPO" --add-reviewer @copilot

This job runs on every push now (synchronize included), so Copilot re-reviews new commits on an open PR instead of only reviewing once at open time. Re-adding an already-requested reviewer is a harmless no-op.

How Copilot's review is scoped

Copilot reviews the PR's diff against main/master, not the whole codebase. For context it reads the full content of changed files and follows imports into files that call the changed code, but it only posts comments on lines that changed — it isn't auditing the rest of the repo.

A fixed set of path patterns is always excluded from review, regardless of repo settings: lockfiles, *.min.js / *.bundle.js, *.svg, *.log, and anything under **/vendor/**, **/generated/**, or **/node_modules/**. That last pattern is what the toggle below relies on.

04 Two toggles built into this repo

Both checks were verified on real, deliberately-broken code before being reset to a quiet state. Neither was deleted — both can be switched back on to demonstrate the pipeline again.

CI failure path

tests/test_ci_failure_check.py

An always-failing assertion, now wrapped in @pytest.mark.skip(...). Remove the decorator and push to make the pytest job fail on demand.

Copilot review path

tests/generated/copilot_review_demo.py

A hardcoded key, a SQL string-concat query, a bare except, and an off-by-one loop. Living under generated/ keeps it out of review; move it out of that directory and push to make Copilot flag it again.

Example — what Copilot actually flagged

Real inline comments Copilot posted on tests/generated/copilot_review_demo.py before it moved under generated/ — one per planted issue:

copilot_review_demo.py:26

copilot_review_demo.py:31

“Using a list as the default argument makes the same buckets object persist across calls, so totals from one invocation leak into later results.”

copilot_review_demo.py:36

“get_first_n returns n + 1 items because range(n + 1) includes the endpoint; it also raises when n equals the input length.”

It also caught things nobody planted: on full-tests.yml it flagged that a fork-originated PR downgrades GITHUB_TOKEN to read-only (breaking the gh pr edit step) and that actions/checkout persists that token in git config by default, which a malicious feature branch could exfiltrate during uv sync/pytest. Real findings, not planted — worth acting on separately from this demo.

Where the results actually show up

LocationWhat you'll see
Actions tab Run status and duration for both jobs, plus a separate “Running Copilot Code Review” entry — that's Copilot's own internal agent run, not this repo's workflow. Neither shows the actual review comments.
PR → Files changed Copilot's inline comments, attached to the exact lines it flagged — the primary place to read findings.
PR → Conversation / Reviewers Copilot's overall review state (commented / approved / changes requested) and a summary comment.
